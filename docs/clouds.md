# Clouds — Implementation Plan (`clouds.md`)

**Status: planned, nothing implemented.** The art exists — 15 cloud bitmaps in
`spritedef.bin` at pointers 80–94, generated by `tools/generate_sprites.py` and
expanded to `$D400` by `mem_init()`. What is missing is everything that decides
*where* a cloud is and *which* hardware sprite draws it.

This document is the implementation plan for
[sprite_objects.md](sprite_objects.md) §2 and §6.1. It does not re-argue the
design decisions made there — hires only, never Y-expanded, dithered white,
clouds occlude the horizon — it commits to numbers and to a code shape.

Two things are being built, and they are separable:

1. **A sprite stack.** A general, distance-sorted allocator for the eight
   hardware sprites in the viewport band. The sun becomes its first client and
   clouds its second; traffic ([planes.md](planes.md)) is meant to be its
   third. This is [sprite_objects.md](sprite_objects.md) §2, and it is worth
   landing on its own, before any cloud exists.
2. **Clouds.** A hashed placement scheme, a group layout, and a distance-driven
   size ladder that feeds candidates into that stack.

---

## 1. The sprite stack

### 1.1. What "closest first" means on a VIC-II

There is no draw order to control. VIC sprite-to-sprite priority is fixed by
index: **sprite 0 draws in front of sprite 1, and so on down to 7.** So
"render the closest objects first" is implemented as *assign the closest object
the lowest index*. Sort the candidates by distance, hand out indices 0, 1, 2 …
in that order, and correct mutual occlusion falls out with no per-frame
priority logic and no writes to `$D01B`.

That also fixes the overflow rule for free. If more objects want sprites than
there are sprites, the ones that lose are the ones at the end of the list —
the farthest — which is exactly the right ones to drop.

### 1.2. The API

```c
// sprites.h

static const uint8_t kSpriteStackSize = 8;
static const uint8_t kSpriteNoBitmap  = 0xFF;

static const uint8_t kSpriteFlagExpandX     = 0x01;   // $D01D
static const uint8_t kSpriteFlagAlignDither = 0x02;   // snap to the grid of §4

// Begin a new frame's candidate list.
void sprites_stack_reset(void);

// Offer one object. Coordinates are viewport screen pixels, origin at the top
// left of the viewport, i.e. the same space gfx_project_and_draw() works in:
//   x = kScreenWidthPixels / 2 - vec_sx
//   y = kViewportEndYPixels / 2 - vec_sy
// and (x, y) is the object's *centre*, not its top left corner.
//
// bitmap2 is kSpriteNoBitmap for a single sprite, or the lower block of a
// 1 x 2 stack, in which case the entry claims two consecutive indices and the
// lower sprite is placed 21 raster lines below the upper one.
//
// The pivot is the bitmap's own, in *sprite* pixels as spritedef.cc stores it;
// the stack applies it, doubling pivot_x when expand_x is set (§3.3).
//
// depth is the camera-space forward distance in 2 m units, used only for
// ordering; INT16_MAX sorts an object behind everything (this is what the sun
// passes). Returns false if the object was culled or did not fit.
bool sprites_stack_add(int16_t depth, int16_t x, int16_t y,
                       int8_t pivot_x, int8_t pivot_y,
                       uint8_t bitmap, uint8_t bitmap2,
                       uint8_t color, uint8_t flags);

// Assign hardware indices nearest-first and publish the result to the raster
// handler. Anything that did not fit is dropped; unused indices are parked.
void sprites_stack_commit(void);
```

`sprites_stack_add()` owns every cull, so no caller repeats them:

- **behind or beside the viewport** — the centre plus the sprite's half-extents
  must intersect the 320 × 112 viewport band;
- **off the left edge** — the X wrap of §1.6, which is a position fix-up plus
  a representability test rather than a plain cull;
- and, for `kSpriteFlagAlignDither`, the position snap of §4.4, applied before
  the culls so a snapped sprite cannot land back outside them;
- **under the message strip** — the existing `_sprites_hidden_by_msg()` box
  test, moved here. [sprite_objects.md](sprite_objects.md) §7 worries that
  eight of these per frame is too many, but the test only runs on candidates
  that already survived the screen cull, of which there are at most eight and
  usually two, and it early-outs on `msg_active()`.

### 1.3. Storage

```c
// Candidate list, main line only. Insertion-sorted by ascending depth.
struct sprite_cand_t {
  int16_t depth;
  int16_t x, y;       // VIC sprite coordinates, top-left, pivot already applied
  uint8_t bitmap;
  uint8_t bitmap2;    // kSpriteNoBitmap for a single sprite
  uint8_t color;
  uint8_t flags;
};
static sprite_cand_t _spr_cand[kSpriteStackSize];
static uint8_t _spr_cand_count;
static uint8_t _spr_slots_used;

// Published form, read by the raster handler. Laid out by register rather
// than by object so the handler is a flat unrolled loop.
struct sprite_frame_t {
  uint8_t x[8], y[8], ptr[8], color[8];
  uint8_t msbx;
  uint8_t expand;
};
static sprite_frame_t _spr_frame[2];
static volatile uint8_t _spr_frame_shown;   // 0 or 1
```

About 120 bytes of `bss2`, of which `_spr_cand` (56 B) is scratch and could be
reclaimed later if it is ever tight. The existing `_sprites_terrain_xy[8]` and
`_sprites_terrain_idx[8]` — declared, never used — are replaced by this.

**The double buffer is not optional.** `_gfx_switch_to_terrain()` reads the
frame from an interrupt at raster 250, while `sprites_stack_commit()` writes it
from the main line at an unrelated point. Today the same race exists for the
sun and covers three bytes, so the worst outcome is the sun one frame stale.
With eight objects a torn read puts one object's X against another's Y, which
is a sprite in the wrong place, not a sprite one frame late. Commit fills the
back frame and then stores `_spr_frame_shown` — a single byte, so the store is
atomic on a 6502 and needs no `sei`.

### 1.4. Changes to the three raster handlers

This is [sprite_objects.md](sprite_objects.md) §2's restructure, and it is what
lets the terrain handler write all eight sprites without a handshake with the
panel code.

| Handler | Raster | Today | After |
| :--- | :--- | :--- | :--- |
| `_gfx_switch_to_terrain` | 250 | sun only: 1 position, 1 pointer pair, 1 colour | all 8: positions, pointer pairs, colours, `$D010`, `$D01D` |
| `_gfx_switch_to_panel_top` | 161 | parks 0–6, places 7 | also clears `$D01D`, also restores sprite 7's colour |
| `_switch_to_panel_bottom` | 186 | places instruments, patches one colour by `#if` | restores all 8 instrument colours unconditionally |

```c
inline void sprites_show_terrain_sprites() {
  const sprite_frame_t *f = &_spr_frame[_spr_frame_shown];
#pragma unroll(full)
  for (uint8_t i = 0; i < 8; i++) {
    vic.spr_pos[i].x = f->x[i];
    vic.spr_pos[i].y = f->y[i];
    *(kScreenRamMain + 1016 + i) = f->ptr[i];
    *(kScreenRamAlt  + 1016 + i) = f->ptr[i];
    vic.spr_color[i] = f->color[i];
  }
  vic.spr_msbx     = f->msbx;
  vic.spr_expand_x = f->expand;
}
```

Roughly 240 cycles against the ~30 the sun costs today. The handler runs at
raster 250 in the bottom border and the only write in it with a deadline is the
`$d018` latch, which comes first; `sound_blit()` already follows it and the
comment in `gfx.cc` accounts for ~200 cycles there with 58 PAL lines to spare.
Another 210 is four raster lines. Fine on PAL; NTSC was already over budget on
that path before this change and stays that way.

**Nothing reached from a raster handler may touch oscar64's runtime zero
page.** This is the constraint that governs how the handler above is written,
and it is not obvious from the C. oscar64 keeps its working registers in the
low zero page - `mem.h`'s comment maps the layout, `ACCU` at `$27`, `TMP` from
`$33` - and those bytes belong to whatever the interrupt landed on top of. A
handler stays clear of them only while every address it touches is a link-time
constant. Two things break that, and both were hit while building phase 1:

- **a pointer variable.** `const sprite_frame_t *f = shown ? &b : &a;` makes
  oscar64 stage the address in `ACCU` and `T1..T3` and read through `(zp),y`.
  The fix is to name the frame in each branch of an `if`, so the base addresses
  are constants and the loop compiles to absolute indexing.
- **more live values than there are registers.** Copying `x[8]` and `y[8]` into
  `$D000` needs two indices at different strides, which is one more than a 6502
  has, and the spill goes to the same zero page. Storing the positions as a
  single `pos[16]` that mirrors `$D000-$D00F` byte for byte reduces it to one
  index and one stride. A loop that counts *down* is also worth having: counting
  up made oscar64 increment the index before the store and shuffle the two
  copies through `ACCU`.

The symptom when this goes wrong is not a wrong sprite. It is
`gfx_update_heading_bitmap()`'s `memcpy` into the panel bitmap running with a
corrupted pointer, and the screen dissolving a long way from the cause.
`tools/check_zeropage.py` does not catch it - that guards the boundary between
oscar64's spilled temporaries and the region `mem.h` claims at `$60`, which is a
different failure. `tools/check_irq_zp.py` guards this one and runs on every
link.

**`_gfx_switch_to_panel_top` is cycle-counted, and both additions land after
its timing-critical block.** The `$d018` / `$d011` / `$d021` stores and the NOP
padding that positions them are untouched; the new work goes inside
`sprites_show_panel_top_sprites()`, which already runs after them. No NOP has to
be removed.

Both additions are needed and neither is obvious:

- **Clearing `$D01D`.** Parking a sprite at `x = 0` hides it because the VIC
  compares X per raster line — but only if it is 24 pixels wide. An X-expanded
  sprite is 48 wide and the left border ends at 24, so parked at 0 it pokes 24
  pixels into the panel. [sprite_objects.md](sprite_objects.md) §1.1's
  parenthetical claims a parked expanded sprite is still hidden; it is not.
  [planes.md](planes.md) §5 has it right.
- **Restoring sprite 7's colour.** Sprite 7 is the vertical-speed needle and it
  is the one instrument visible in the panel-top band. Once the terrain handler
  writes all eight colours, sprite 7 arrives at raster 161 holding a cloud's
  white instead of `kColorInstrument`.

### 1.5. One more latent bug to fix while here

`$D017` (Y-expand), `$D01C` (multicolour), `$D01D` (X-expand) and `$D01B`
(sprite/background priority) are **never written anywhere in the codebase.**
Today that works because they are zero after a reset and nothing needs them
otherwise. The moment `$D01D` becomes a live register, relying on the others'
reset state is no longer defensible — `map.cc` already carries a comment noting
`spr_multi` is never set. Add to `sprites_init()`:

```c
vic.spr_expand_x = 0;
vic.spr_expand_y = 0;   // never used, by anything, ever (sprite_objects.md §0)
vic.spr_multi    = 0;   // hires only (sprite_objects.md §0)
vic.spr_priority = 0;   // sprites in front of the terrain
```

### 1.6. The left edge, and the X wrap

A sprite's X register is 9 bits and there is no negative X, so a sprite
straddling the left edge looks unrepresentable. It is not: the VIC's horizontal
counter does not start at the left of the picture. A PAL raster line is 63
cycles — **504 counter positions** — and the line *begins* around counter 404,
so the counter runs 404 … 503 and then wraps to 0 … 403 within the same line.
Counter values just under 504 are therefore physically immediately to the left
of counter 0, and the visible sequence along one line is

```
   ... 488 .. 503 | 0 .. 23 | 24 .. 343 | 344 ...
       left border  left bdr   screen      right border
```

So the register is a ring, and placing a sprite off the left edge is one
conditional add:

```c
// sx = the sprite's left edge in viewport screen pixels, signed.
int16_t vx = sx + kSpriteOffsetX;              // kSpriteOffsetX = 24
if (vx < 0) vx += kSpriteXWrap;                // kSpriteXWrap = 504 (PAL)
```

with two culls, both in signed screen space before the wrap:

```c
if (sx >= (int16_t)kScreenWidthPixels) return false;   // off the right
if (sx + ink_w <= 0)                   return false;   // nothing left to show
if (sx < kSpriteSxMin)                 return false;   // not representable
```

`kSpriteSxMin = kSpriteXWrapFirst − kSpriteXWrap − kSpriteOffsetX`, which for
`kSpriteXWrapFirst = 488` is **−40**: a sprite may hang 40 pixels off the left
edge before the wrap runs out of room.

**Cull on the ink, not on the sprite box.** `generate_sprites.py` centres each
cloud in its 24-column grid (`start_sx = 12 − w_world / 2`), so a rung-0 cloud
is 6 pixels of ink inside a 48-pixel expanded sprite with 21 blank pixels on
each side. Testing the sprite box would cull it while it is still fully on
screen. With the ink box, only rung 9 — 21 world pixels, ink at 4 … 45 within
the sprite — reaches `kSpriteSxMin` at all, and it does so with about 6 pixels
of cloud still showing, against 24 for the naive cull. **The sun stops popping
entirely**: unexpanded and 21 pixels of ink, it runs out of ink at `sx = −21`,
well inside the −40 limit, so it slides off completely smoothly.

**The wrap and the dither snap commute, and not by accident.** §4 needs `X_vic`
even and `(X_vic >> 1) + Y_vic` even. `kSpriteXWrap` is 504, and **504 is
divisible by 4**, so adding it preserves both the parity of `X` and the parity
of `X >> 1`. The snap can therefore be done in signed screen space in
`sprites_stack_add()` and the wrap applied later, in `sprites_stack_commit()`,
when the value is packed into `sprite_frame_t` — no interaction to reason
about, and no re-snap after wrapping. Had the line been 502 or 510 counters
long this section and §4 would be in conflict.

The wrapped values are all ≥ 256, so they set their `$D010` bit; the panel
handlers already clear `$D010` wholesale when they park, so nothing there
changes.

**`kSpriteXWrapFirst` is a measured constant, not a derived one.** Where the
left border actually begins in counter terms varies with VIC revision, and the
504 modulus is PAL — an NTSC line is 520 counters, which does not fit the
9-bit register at all, so the wrap does not transfer. Measure it once in VICE
with a test sprite, put it in `sprites.h` next to `kSpriteOffsetX`, and let the
cull derive `kSpriteSxMin` from it rather than hardcoding −40. The project
already treats NTSC as second-class (`gfx.cc`, on the flip window), and this is
one more place where it is.

### 1.7. What the sun becomes

An ordinary entry:

```c
sprites_stack_add(INT16_MAX, sx, sy,
                  kSpriteDefSun.pivot_x, kSpriteDefSun.pivot_y,
                  kSpriteDefSun.bitmap_idx, kSpriteNoBitmap,
                  kColorSun, /*flags=*/0);
```

`sprites_set_sun_position()`, `_sprites_sun_x/_y/_msbx` and `kSpriteIdxSun` all
go away, and with them the `kSpriteIdxThrottle == kSpriteIdxSun` and
`kSpriteIdxFuel == kSpriteIdxSun` special cases in
`sprites_show_panel_bottom_sprites()`.

One behavioural change comes for free and is an improvement:
[sprite_objects.md](sprite_objects.md) §1.1 notes the sun's
`y >= kRasterScreenYStart + kViewportEndYPixels` test culls an object that could
legally be shown partially. The stack's cull is *does the sprite's box
intersect the viewport band*, so an object straddling the panel edge is now
clipped at raster 161 by the parking, not hidden whole.

## 2. Where clouds are

### 2.1. Units, and why they are the terrain's

`flight_eye_*` is 24.8 fixed point in metres; `world.cc` down-shifts by 9, so
the terrain grid works in **2 m units** and a `uint16_t` position wraps at
131 km. Clouds use the same units.

[planes.md](planes.md) §2 argues traffic must *not*, and the argument does not
carry over. Its problem is that an aircraft a hundred metres away turns one
unit of rounding into 7 px of frame-to-frame jitter. A cloud is never a hundred
metres away in a way that matters — the nearest rung of the ladder is at
1,170 m — and at 4 km one 2 m unit is 0.13 px. Two metres is plenty.

### 2.2. The cell grid

The world map is 16 × 32 tiles of 1024 units (2,048 m), wrapping
([world.h](../c64o/world.h)). Clouds use a grid **two map tiles on a side**:

| | Value |
| :--- | ---: |
| Cloud cell | 2048 units = 4,096 m |
| Cells in the world | 8 × 16 = 128 |
| Cell index | `(mx >> 11) & 7`, `(my >> 11) & 15` |
| Scan | 5 × 5 cells around the eye |
| Guaranteed scan radius | 2 × 2048 = 4096 units = **8,192 m** |

The scan radius and the cull radius have to be **the same number**, and this is
the constraint that sets the cell size. A group found outside the guaranteed
radius would appear and disappear as the eye crossed a cell boundary rather
than as it moved — a flicker keyed to nothing the pilot can see. So the cull
happens at 4,096 units even though the 5 × 5 block usually reaches 8,192.

A 3 × 3 scan would be cheaper but guarantees only one cell of radius, which for
any workable cell size is either far too short a draw distance or far too
coarse a grid.

Cell coordinates follow `world.cc`'s convention exactly: the *unmasked* cell
index builds the world position, the *masked* one indexes the hash, so the
position arithmetic is plain `int16_t` subtraction and needs no wrap handling.

### 2.3. The hash

Zero RAM for the layout, an unbounded number of clouds, and the same cloud in
the same place every time you fly past it.

```c
// clouds.cc
static const uint8_t kCloudHashX[8]  = { ... };   // 8 scramble bytes
static const uint8_t kCloudHashY[16] = { ... };   // 16 scramble bytes
static const uint8_t kCloudHashA[32] = { ... };   // presence + pattern
static const uint8_t kCloudHashB[32] = { ... };   // jitter x, jitter y

static const uint8_t kCloudGateMask = 0x03;       // 1 cell in 4 has a group

inline bool _cloud_at(int8_t cx, int8_t cy, uint8_t *ha, uint8_t *hb) {
  uint8_t a = kCloudHashX[cx & 7] ^ kCloudHashY[cy & 15];
  *ha = kCloudHashA[a & 31];
  if ((*ha & kCloudGateMask) != 0) return false;
  *hb = kCloudHashB[a & 31];
  return true;
}
```

Two ANDs, two XOR-ed table reads, a third read, a mask and a branch — call it
25 cycles, and 24 of the 25 cells stop there.

**Presence and jitter must come out of different tables, not different bits of
the same byte.** Gating on `h < threshold` and then taking `h >> 3` for a jitter
correlates the two: every cell that has a cloud also has a small jitter, and
the layout gets a visible diagonal grain. Two tables indexed by the same
scrambled byte cost 32 extra bytes and remove the problem.

Fields of the two bytes:

| Field | Bits | Use |
| :--- | :--- | :--- |
| gate | `ha & 3` | present when zero |
| pattern | `ha >> 6` | which of 4 group layouts (§2.5) |
| jitter x | `hb & 0x0F` | × 128 units, spans the cell |
| jitter y | `hb >> 4` | × 128 units, spans the cell |

Constants get generated, not hand-typed — see §7.

### 2.4. Density

`kCloudGateMask = 0x03` puts a group in one cell in four: about 32 groups in
the world. Sampled over 4,000 random positions, headings and altitudes:

| Gate | Cells with a group | E[groups in view] | P(0) | P(1) | P(≥2) |
| :--- | ---: | ---: | ---: | ---: | ---: |
| `0x07` (1 in 8) | 0.15 | 0.39 | 0.65 | 0.31 | **0.04** |
| **`0x03` (1 in 4)** | **0.20** | **0.50** | **0.58** | **0.36** | **0.07** |
| `0x01` (1 in 2) | 0.48 | 1.25 | 0.18 | 0.46 | 0.36 |

`0x03` is the recommended default: you see a cloud group about 40% of the time
and two at once about 7% of the time, which is the brief. The numbers barely
move with altitude, which is the point of §2.6's deck height.

### 2.5. A group is three blobs

Three blobs whose spacing is about half a blob diameter, so they overlap
wherever you look at them from. Offsets are built in **world** axes, not
camera axes, so the group has a fixed shape in the world and rotates with the
camera the way a real cloud does.

Doing that naively costs a `vec_transform_inv` per blob. Instead, borrow
`world.cc`'s trick: transform the *basis* once per frame and add.

```c
// Camera-space image of a world-axis displacement of kCloudOffsetU units.
// vec_transform_inv(cam, (k,0,0)) is (front.x, left.x, up.x) * k / 256, so
// this is nine multiplies for all three axes, not twenty-seven.
static vec3_t _cl_ex, _cl_ey, _cl_ez;      // full step
static vec3_t _cl_hx, _cl_hy;              // half step, a shift each
```

Then a blob is the group centre plus a fixed integer combination of those —
adds and negations only, no multiplies:

| Pattern | Blob A | Blob B | Blob C |
| :--- | :--- | :--- | :--- |
| 0 | `−ex −½ey` | `+ex −½ey` | `+ey +½ez` |
| 1 | `−ey −½ex` | `+ey −½ex` | `+ex +½ez` |
| 2 | `−ex +½ey` | `+ex +½ey` | `−ey +½ez` |
| 3 | `−ey +½ex` | `+ey +½ex` | `−ex +½ez` |

Four patterns from `ha >> 6`; they are the same triangle at four orientations,
which is enough variety for something you see one of at a time.

The `½ez` on the third blob is a deliberate small departure from "all at the
same altitude": a purely horizontal triple reads as a row of dots from the
side. At `kCloudOffsetU = 48` units the lift is 48 m, which is a bump on top of
the group, not a second deck.

**All three blobs of a group share one ladder rung**, chosen from the group
centre's depth (§3.2). They are within 100 m of each other at a range of
kilometres, so computing three rungs would produce the same answer three times.

### 2.6. Deck altitude

**`kCloudDeckU = 350` units = 700 m**, one constant, no per-group variation.

This is the decision the whole feature turns on, and the reason is the
viewport, not meteorology. The viewport is 320 × 112 screen pixels and
`vec_project` scales by 256, so the vertical field of view is **±12.3°** —
against ±32.0° horizontally. In level flight a cloud whose altitude differs
from the eye's by Δz only enters the viewport once

```
D > 256 · Δz / 56  =  4.57 · Δz
```

so a realistic 1,500 m deck seen from 100 m needs 6.4 km of horizontal
separation just to be on screen, and by then it is at the cull. A high deck
would be a feature you almost never see.

At 700 m the deck is inside the band the aircraft actually flies in:

| Eye altitude | Δz | Deck enters the viewport beyond | Live annulus |
| ---: | ---: | ---: | :--- |
| 100 m | 600 m | 2,743 m | 2.7 – 8.2 km |
| 400 m | 300 m | 1,371 m | 1.4 – 8.2 km |
| 700 m | 0 | always | 0 – 8.2 km |
| 1,200 m | −500 m | 2,286 m | 2.3 – 8.2 km, below the horizon |

and you fly under it, through it and over it in a normal climb.

## 3. How big a cloud is

### 3.1. The size follows from the ladder, not the other way round

`vec_project` gives `sx = 256·y/x`, used as a pixel offset directly, so an
object of size `S` spans `256·S/D` screen pixels — `128·S/D` world pixels, the
unit `generate_sprites.py` sizes the cloud bitmaps in.

The ladder is fixed: ten rungs, world-pixel widths 3, 5, 7 … 21, the first five
a single sprite and the last five a 1 × 2 stack. Two constraints pin the blob
diameter:

- the **smallest** rung should land at the cull radius, so a cloud fades in by
  stepping up the ladder rather than popping (§6.1 of
  [sprite_objects.md](sprite_objects.md));
- the cull radius is fixed at 4,096 units by §2.2.

`w = 3` at `D = 4096` gives `S = 3 · 4096 / 128 = 96` units, so:

**`kCloudBlobU = 96` units = 192 m diameter**, a group about 400 m across —
a fair-weather cumulus.

### 3.2. Rung selection is a compare chain, not a divide

Because `S` is a constant, the rung is a pure function of depth, and the
thresholds are constants:

```c
// Largest camera-space depth (2 m units) at which each rung still applies.
// kCloudRungDepth[i] = 128 * kCloudBlobU / (3 + 2 * i)
static const int16_t kCloudRungDepth[10] = {
    4096, 2458, 1755, 1365, 1117, 945, 819, 723, 647, 585 };
```

| Rung | World px | Screen px | Depth ≤ | Distance |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 3 × 5 | 6 × 5 | 4096 | 8,192 m |
| 1 | 5 × 9 | 10 × 9 | 2458 | 4,915 m |
| 2 | 7 × 13 | 14 × 13 | 1755 | 3,511 m |
| 3 | 9 × 17 | 18 × 17 | 1365 | 2,731 m |
| 4 | 11 × 21 | 22 × 21 | 1117 | 2,234 m |
| 5 | 13 × 25 | 26 × 25 | 945 | 1,890 m |
| 6 | 15 × 29 | 30 × 29 | 819 | 1,638 m |
| 7 | 17 × 33 | 34 × 33 | 723 | 1,446 m |
| 8 | 19 × 37 | 38 × 37 | 647 | 1,293 m |
| 9 | 21 × 41 | 42 × 41 | 585 | 1,170 m |

```c
if (depth > kCloudRungDepth[0]) return;      // beyond the cull
uint8_t rung = 0;
while (rung < 9 && depth <= kCloudRungDepth[rung + 1]) rung++;
```

Ten compares worst case, no division, and the cull is the same test as the
fade-in. Rungs 0–4 index `kSpriteDefCloud1Sprite[rung]`; rungs 5–9 index
`kSpriteDefCloud2Sprite[rung - 5]`.

Depth here is camera-space forward `x`, not the radial distance. A cloud at the
edge of the frame is therefore up to 18% oversized. Using the true range would
cost a square root; the error is a size the eye has nothing to compare against,
so `x` it is.

Inside 1,170 m the rung clamps and the cloud stops growing, the same device as
[planes.md](planes.md) §4's size cap — cropping a cloud would show the middle
of a cloud.

### 3.3. Pivots and the X-expansion trap

Every cloud sprite is X-expanded (`sprite_objects.md` §6.1). **The pivot in
`sprite_cloud1_meta_t` / `sprite_cloud2_meta_t` is in sprite pixels, and an
expanded sprite pixel is two screen pixels**, so the horizontal pivot must be
doubled and the vertical one must not:

```c
spr_x = screen_x + kSpriteOffsetX - 2 * meta->pivot_x;   // = screen_x, since
                                                         // pivot_x is 12 and
                                                         // kSpriteOffsetX is 24
spr_y = screen_y + kSpriteOffsetY -     meta->pivot_y;
```

That the two constants cancel exactly for every cloud bitmap is a coincidence
of `pivot_x = 12`, and the code should not lean on it.

For a two-sprite entry the lower sprite goes at `spr_y + 21` and shares the
X register, the colour and the expansion. `pivot_y` is 20 for the stacked
bitmaps, which puts the blob's centre one line into the lower sprite —
`generate_sprites.py` slices the concept art at row 100 of a 79–120 band, so
this is already right and needs no adjustment.

## 4. The dither must share one grid

### 4.1. What goes wrong

A cloud is a 50% white-and-transparent checkerboard
([sprite_objects.md](sprite_objects.md) §6.1), and §2.5 deliberately puts three
of them on top of each other. Sprite-to-sprite priority means the nearer
sprite's *transparent* pixels let the farther one show through, so what the
overlap looks like is decided entirely by whether the two checkerboards are in
phase.

Measured on the real bitmaps, over the region where two rung-4 blobs overlap:

| Relative offset | Coverage in the overlap | Reads as |
| :--- | ---: | :--- |
| both even, or both odd | **48%** | one cloud, uniform half-tone |
| either one odd | **82%** | a solid white lump with a hard edge where the overlap stops |

Out of phase, the rear sprite fills exactly the holes the front sprite left.
That is the worst available outcome: the dither exists so a cloud does not read
as a cut-out, and the overlap is where the group is meant to look most like a
cloud, not least. It is also not a subtle artefact — the two states differ by
the entire point of the art, and the boundary of the overlap region draws a
visible rectangle across the group.

So the requirement is that **every cloud sprite on screen, in every frame,
lands on one global checkerboard lattice.** Not each sprite internally
consistent — all of them consistent with each other.

### 4.2. The invariant

Two halves, one in the generator and one at runtime.

Write the bitmap's own column and row as `c`, `r`. Every cloud sprite is
X-expanded, so a bitmap column is two screen pixels wide and a bitmap row is
one raster line. Let

```
W0 = (X_vic - kSpriteOffsetX) / 2     // the sprite's leftmost world-pixel column
R0 =  Y_vic - kSpriteOffsetY          // the sprite's top raster line
```

A lit pixel is then at world column `W0 + c` and line `R0 + r`. If the bitmap's
own rule is *set iff `(c + r)` is even*, the on-screen phase of the whole
sprite is `(W0 + R0) mod 2` — one bit, and it is the only thing that has to
agree between sprites.

- **Bitmap half.** Every set bit in every cloud bitmap satisfies
  `(c + r + 21·is_lower) ≡ 0 (mod 2)`, where the `21` carries the lower block
  of a 1 × 2 stack across the seam.
- **Position half.** For every cloud entry, `X_vic` is even and
  `(X_vic >> 1) + Y_vic` is even.

`X_vic` must be even on its own account, not just as part of the sum: an
X-expanded sprite at an odd `X_vic` puts its pixel columns on odd screen
pixels, half a world pixel out of step with every other cloud. That does not
flip the phase, it interleaves the two dithers at half-pixel offsets, which
takes the overlap to 75% and cannot be corrected by any choice of `Y`.

Substituting: `W0 + R0 = X_vic/2 − 12 + Y_vic − 50`, and 62 is even, so the
condition really is just `(X_vic >> 1) + Y_vic` even. Which of the two phases
is "the" phase is arbitrary; even is as good as odd.

### 4.3. The bitmaps already satisfy it — pin it down

Checked over all 15 generated blocks in `lib/spritedef.py`: **zero set bits
violate the rule**, on the single sprites, on the upper blocks and on the lower
blocks across the 21-line seam.

What makes the runtime rule a pure position snap, with no per-bitmap correction
term, is that all fifteen blocks share **one** phase — not anything about the
pivots. An earlier draft of this section said the pivots' even coordinate sums
were load-bearing; they are not. `sprites_stack_add()` subtracts the pivot
*first* and snaps the sprite's top left, so the pivot never enters the lattice
arithmetic. It is worth checking anyway, for a different reason: the rungs are
a size ladder the renderer steps up and down as a cloud approaches, and a rung
whose pivot disagreed with its neighbours would make the blob jump sideways at
the step instead of just growing.

That is currently a **property of `gfx/ppilot_clouds_concept.png` and of the
crop rectangles in `generate_sprites.py`, and nothing enforces it.** The
extraction ORs two horizontally adjacent source pixels
(`img[y][x] or img[y][x+1]`), which happens to be a no-op because the art is
already drawn at world-pixel resolution — but redraw the concept at 1-pixel
resolution and that OR turns the checkerboard solid, silently. Move the crop
box by one pixel and the phase inverts, silently, for one rung only.

Two changes make it structural rather than lucky:

1. **Apply the dither in the generator, not in the PNG.** Build a coverage mask
   from the art exactly as now, then `AND` it with the canonical checkerboard
   `((c + r + 21·is_lower) & 1) == 0`. Because the current bitmaps already have
   zero violations this is provably byte-identical today — a no-op change that
   can be verified against the checked-in `spritedef.bin` — and afterwards the
   phase is a property of the generator. The art is then free to be a plain
   silhouette.
2. **Assert it.** `generate_sprites.py` fails the build if any set bit or any
   pivot violates the rule, and a case in `tests/` re-checks it against
   `lib/spritedef.py`. This is the invariant most likely to be broken by
   someone editing the art with no idea it exists, and the failure is silent on
   the generator side and unmistakable on screen.

### 4.4. The runtime snap

```c
// Cloud entries only. x is 9-bit, so bit 1 lives in the low byte.
x &= ~1;                              // land on the world-pixel grid
y  = (y & ~1) | ((x >> 1) & 1);       // bit 0 of y := bit 1 of x
```

Four instructions, once per entry in `sprites_stack_add()`, gated on
`kSpriteFlagAlignDither`. Nothing else needs to know about it — the sun does
not set the flag, and the instrument sprites never go through the stack.

The lower sprite of a 1 × 2 stack is placed at `y + 21` as usual and needs no
separate treatment: 21 flips the row parity, and the bitmap's own phase was
built with the same 21 in it (§4.2), so the two cancel and the stack is
continuous across the seam. Verified on the generated blocks, not assumed.

### 4.5. What it costs

**Horizontally, nothing.** Snapping `X` to even puts a cloud's expanded pixels
exactly on the 2-screen-pixel world-pixel columns that `gfx.cc` already
quantises terrain dots to (`(px & 0x06) >> 1`). The cloud dither and the
terrain dots end up on one lattice, which is a small bonus rather than a
compromise — and it is the granularity
[sprite_objects.md](sprite_objects.md) §3 says an expanded sprite pixel matches
by construction.

**Vertically, one raster line of quantisation — which turns out to be free
too.** Cloud `Y` becomes even-or-odd by rule instead of free, so a cloud's
vertical position is precise to two raster lines rather than one. Two raster
lines is exactly the terrain's own vertical lattice: `gfx.cc` selects a dot
character with `((lpy & 0x06) << 1)`, four sub-positions over eight lines, and
`generate_gfx_chars.py` draws each dot two lines tall
(`char_bytes[y*2]` and `char_bytes[y*2+1]`). So after the snap a cloud sits on
the same 2 × 2 screen-pixel lattice the terrain dots do, on both axes. The
snap does not cost alignment with the world; it buys it.

**A sub-pixel relative wobble between blobs.** Each blob snaps independently,
so as a group drifts across the screen its blobs cross their snap boundaries at
different moments and their spacing changes by up to one pixel and one line.
At 10 Hz against a 26–42 pixel blob this should be invisible. If it is not,
the fix is to snap the *first* blob of a group and then round each remaining
blob's offset *from that blob* onto the same lattice, which makes the group
rigid for one subtraction per blob — the same operation applied to a delta
instead of an absolute.

**A half-pixel bias.** `x &= ~1` always rounds left and the `y` adjustment
always rounds one way. Rounding to nearest is a `+1` before the mask and is
worth doing, but the bias is uniform across every cloud and therefore invisible
either way; consistency is what matters, not the direction.

### 4.6. The alternative that does not fit

The obvious other answer is to keep `Y` free and carry **two bitmap sets of
opposite phase**, choosing whichever matches the position. It does not fit:
`$D400–$D7BF` is exactly 15 blocks and the ladder already uses all 15
([sprite_objects.md](sprite_objects.md) §6.1). Thirty blocks would have to
displace the needles or move to plain RAM, and the whole point of putting cloud
art under I/O is that it is written once and never touched again. One raster
line of quantisation is much the cheaper price.

## 5. Per-frame cost

`clouds_add_candidates()` runs once per `flight_advance`, at the wobbling
~10 Hz that makes a sim frame ~98,500 cycles
([planes.md](planes.md) §11), whose measured figures the estimates below use.

| Step | Cycles | When |
| :--- | ---: | :--- |
| Offset basis (9 multiplies, 6 shifts) | ~510 | once per frame |
| 25 hash gates | ~625 | once per frame |
| Relative position + Manhattan reject | ~90 | per surviving cell |
| `vec_transform_inv` of the group centre | ~450 | per group |
| Rung compare chain | ~80 | per group |
| Blob offset adds | ~60 | per blob |
| `vec_project` | ~350 | per blob |
| Screen → sprite, culls, stack insert | ~160 | per blob |
| `sprites_stack_commit()` | ~250 | once per frame |

| Situation | Cycles | Share of a sim frame |
| :--- | ---: | ---: |
| No group in range (58% of frames) | ~1,400 | 1.4% |
| One group, three blobs | ~3,700 | 3.8% |
| Two groups (7% of frames) | ~5,900 | 6.0% |

For comparison the sun costs ~850 cycles today and keeps costing it. The
dominant term when nothing is visible is the 25 hash gates, which is the price
of the wide scan radius §2.2 argues for.

Sampling the slot demand over 6,000 random frames at the recommended density:
mean 1.7 of 7 cloud slots, 89% of frames want three or fewer, and **1.5% of
frames want more than seven** — the case the stack's drop rule exists for, and
rare enough that dropping the farthest blob is invisible.

None of [sprite_objects.md](sprite_objects.md) §5's mitigations are needed at
this budget. Its round-robin candidate scan in particular should not be built:
the scan is 625 cycles and spreading it over frames buys nothing worth the
state it would need.

## 8. Tests

The stack is pure logic over integers and the placement is a pure function of
position — both build on the host, so most of this is testable without an
emulator.

Assert on the **VIC registers**, not on the frame struct. `vic.h` and `mem.h`
point their register and screen-RAM addresses at arrays when `__OSCAR64__` is
not defined — the device `sid.h` already uses for the SID — so a band handler
can be called on the host and what it programmed read straight back. That also
puts the §1.4 restructure under test, which is the part of phase 1 with the
least margin for error.

Two things this cannot see, and it should say so rather than imply coverage:
whether a handler touches oscar64's runtime zero page (§1.4 — that is
`tools/check_irq_zp.py`), and anything about raster timing.

**Sprite stack**

- nearest candidate gets index 0, farthest gets the highest used index;
- the sun at `INT16_MAX` always lands last;
- a two-sprite entry gets consecutive indices and the lower sprite is exactly
  21 lines below the upper;
- overflow drops the farthest, never a nearer one, and never leaves a partly
  written entry;
- unused indices are parked at `x = 0` with the expansion bit clear;
- no index is used twice — the property most likely to break silently;
- a cloud-flagged entry always comes out with `X` even and `(X >> 1) + Y` even,
  for a sweep of every raw input position — the §4.2 position half, and the
  cheapest place to catch a regression in it.

**Dither phase**

- every set bit of all 15 blocks satisfies `(c + r + 21·is_lower) ≡ 0 (mod 2)`,
  stated both per block and on the assembled 42-row stack, plus the stronger
  form the runtime actually depends on: all fifteen share *one* phase. Runs
  against `lib/spritedef.py` in `tests/`, so it fails on `make sprites`, not on
  screen;
- regenerating reproduces the checked-in `c64o/spritedef.bin` byte for byte,
  **and** the metadata matches `lib/spritedef.py`. The second half is not
  redundant: pivots and block indices never reach the `.bin`, so the byte
  comparison structurally cannot see a changed pivot;
- **feeding the generator art with no checkerboard in it still produces one.**
  This is the test for what §4.3 actually bought — before it, the phase came
  from the concept PNG, and a silhouette redrawn solid would have come out as
  solid white blobs;
- two blobs at every relative offset in a ±24 × ±21 sweep. The strong form is
  exact rather than statistical: every lit pixel has an even coordinate sum, so
  an odd `(dx + dy)` puts every pixel of the shifted copy on the *odd*
  sublattice and the two lit sets are **disjoint** — which is precisely "the
  rear sprite fills the front one's holes". The 48%-against-82% coverage figure
  of §4.1 is checked too, with loose bounds, so the number in the prose stays
  honest if the art is ever redrawn;
- and the guards themselves: `assert_dither_phase()` and
  `assert_pivots_consistent()` are each fed something they must reject.

**The X wrap**

- for a sweep of `sx` from `kSpriteSxMin` to `kScreenWidthPixels`, the packed
  register is in `[0, 503]` and the sprite's visible span is exactly the
  intersection of `[sx, sx + ink_w)` with `[0, 320)`;
- the cull boundaries are the ink box, not the sprite box — a rung-0 cloud at
  `sx = -20` survives, a rung-9 cloud at `sx = -44` does not;
- wrapping preserves the §4.2 position invariant, i.e. `504 % 4 == 0` is
  asserted rather than assumed, and snap-then-wrap equals wrap-then-snap for
  every input.

**Placement**

- the hash is stable, and wraps: cell `(cx, cy)` and `(cx + 8, cy + 16)` give
  the same group;
- measured density matches §2.4 within sampling error;
- presence and jitter are uncorrelated — a χ² over the joint distribution,
  which is the test that would have caught the single-table version;
- the rung is monotone non-increasing in depth and never indexes outside the
  ten-rung table;
- no candidate survives beyond the cull radius, and the cull radius is ≤ the
  scan's guaranteed radius. **This assertion is the one that fails if someone
  retunes the cell size** and it should name §2.2 in its message.

**On the C64**

- `bm_start()` / `bm_end()` around `clouds_add_candidates()` — §5 is arithmetic
  from operation counts, exactly the kind of estimate
  [sprite_objects.md](sprite_objects.md) §8 asks to be measured before it is
  treated as settled;
- fly a full circle at 700 m and confirm nothing flickers at cell boundaries —
  the §2.2 failure mode;
- check the panel band is clean with a large cloud straddling raster 161: the
  `$D01D` clear (§1.4) is the thing being tested and its failure is 24 pixels of
  white in the instrument panel;
- check sprite 7 is the right colour while a cloud is up — the other half of
  §1.4.

## 10. Open questions

Most of what was open here has been decided; the answers are kept rather than
deleted, in the style [sprite_objects.md](sprite_objects.md) §8 uses, so a
later reader can see what was considered.

- ~~**The left-edge pop.** Is the `$1F8` X-wrap worth implementing?~~
  **Answered — yes, and it is designed in §1.6.** It removes the sun's pop
  outright and reduces a rung-9 cloud's from 24 pixels to about 6. The
  favourable part is that 504 is divisible by 4, so the wrap cannot disturb the
  dither lattice of §4.
- ~~**Is 4 patterns enough (§2.5)?**~~ **Answered — yes.** One group is visible
  at a time in 84% of frames with a group in view, so the repetition has
  nothing to be compared against. `ha >> 4` remains available if that ever
  changes.
- ~~**Is the per-blob snap wobble visible (§4.5)?**~~ **Deferred, deliberately.**
  Ship the independent per-blob snap; build the rigid-group version only if a
  screenshot demands it. It is one subtraction per blob and can be added
  without disturbing anything else.
- ~~**Is 700 m the right deck (§2.6)?**~~ **Provisional, and cheap to change.**
  It is a single constant and §2.4's density is insensitive to it, so it can be
  retuned after flying rather than before.
- ~~**Should the group's third blob keep its `½ez` lift (§2.5)?**~~
  **Answered — keep it.** 48 m of lift is what stops a group reading as a row
  of dots from the side.
- ~~**The 4:1 vertical granularity mismatch**
  ([sprite_objects.md](sprite_objects.md) §3).~~ **Answered — the premise is
  wrong, and the correction belongs in that document.** §3 says the terrain dot
  characters "put each plotted dot in a 4 × 4 screen-pixel quadrant, i.e. 4
  raster lines tall". Both halves are off by two. `gfx.cc` picks the dot
  character with `((lpx & 0x06) >> 1) + ((lpy & 0x06) << 1)` — four
  sub-positions per axis over an 8 × 8 cell, so **2 × 2 screen pixels each**,
  not 4 × 4 — and `generate_gfx_chars.py` confirms the glyph, one multicolour
  pixel wide (`alt_lines[x]`, 2 screen pixels) and two raster lines tall
  (`char_bytes[y*2]`, `char_bytes[y*2+1]`). What "16 variants per group" buys
  is a 4 × 4 *arrangement*, not a 4 × 4 pixel.

  So the real numbers are: horizontally an X-expanded sprite pixel is 2 screen
  pixels and so is a terrain dot — **1:1**, as §3 already says elsewhere.
  Vertically an unexpanded sprite pixel is one raster line against the dot's
  two — **2:1**, and only on that one axis. That is a factor the eye has no
  reference for, and §4.5 makes it moot for clouds anyway, since the dither
  snap puts them on the terrain's own 2 × 2 lattice. Not a problem, and
  `sprite_objects.md` §3's paragraph and §8's question should both be corrected
  to say so.
